The brief

A visitor walks up.
Nobody is there to help them.

A museum kiosk has to identify a stranger, run a camera-guided meditation session, hand them a personal report, and reset itself — unattended, all day.
No staff present
No keyboard

Two teams, one thin seam

HARDWARE TEAM  (IITH)

Cameras, servos, CV

RealSense and thermal capture, posture and gaze analysis, and the meditation-app that produces the report PDF.

MINE

The hard part

How do you identify
someone with no scanner?

Every obvious answer costs hardware: a QR reader, a card reader, a touchscreen keyboard that needs cleaning between strangers.
04
Design evolution

Three attempts

01

Data in the QR

The printed code carried the visitor's details. Fully offline — but still needs a reader at the kiosk, and puts personal data on paper.

02

QR holds an id

The code became a lookup key and the kiosk fetched details over the API. Better privacy — the scanner problem remained.

03  ·  SHIPPED

Invert it

The kiosk shows the QR and the visitor's phone scans it. The phone is the scanner, camera and keyboard. Zero hardware.

05
The decision that mattered

The phone
is the scanner

The kiosk asks the backend for a session, renders the token as a QR, and polls. The visitor's own phone does the reading.
POST /api/sessions
GET /api/sessions/:token
A constraint produced a simpler design than a budget would have.
06
End to end

Four stages, one API

STAGE 01

Identify

An admin roster gives each person a private link. They open it on their phone and scan the kiosk.

GET /api/people/:token
POST /api/claim
STAGE 02

Claim

The backend links that identity to the kiosk's open session. The polling kiosk advances by itself.

GET /api/sessions/:token
-> status claimed
STAGE 03

Session

The kiosk launches the CV pipeline and blocks. This boundary is deliberately not an API.

bash scripts/run1.sh
writes report.pdf
STAGE 04

Report

The newest PDF written after the session began is rendered in-app, then the kiosk resets.

PDFium -> page images
Kiosk to Backend is the only network boundary — plain REST over HTTPS.
Kiosk to meditation-app is a local process and a file on disk. No protocol to break.
07
Running system

09
Debugging

Three that cost me days

WAYLAND

Fullscreen refused

CanResize="False" sets fixed size hints, and the compositor then refuses to fullscreen the window. The intuition is backwards.

DEPENDENCIES

A clash that hides

Avalonia and the PDF renderer both use SkiaSharp. I verified they resolved to one version before committing to in-app rendering.

THE BEST ONE

“Can't reach the server”

The VM clock was in the past, so valid HTTPS certificates looked not yet valid. Nothing to do with the server at all.

10
Testing

Building it
without the hardware

For most of the internship there were no cameras and no meditation-app. The flow still had to be testable.
Two environment variables swap the pipeline for a mock. No test code inside the app, nothing extra in the shipped package — and those same variables are the real production override.
$ export DIYA_PIPELINE_SCRIPT=…/run1.mock.sh
$ export DIYA_REPORT_DIR=/tmp/diya-reports
$ diya-meditation

Calibrating cameras…
Running t3 (PDF report)…
All tasks completed successfully.
Login, session, report, thank-you, on any Linux desktop.

Shipping

A single package

Self-contained .deb for amd64 and arm64. The museum machine needs nothing pre-installed.

LOCK DOWN

A kiosk, not an app

systemd user service with Restart=always, autologin, and GNOME escape shortcuts disabled.

DEPLOY

Backend in one file

A blueprint provisions the web service and Postgres together, then tracks main.

Plus documentation written for whoever comes next: an overview, a full command reference, an FAQ, and a handoff note recording the dead ends so nobody repeats them.
